## Method and measurement limits

Real headed Chromium, local Vite, 44.1 kHz AudioContext. Nine tracks use deterministic 8 ms, amplitude 0.02 pulse buffers. Phrases 0, 1 and 3 contain all 64 steps, exercising boundaries, empty-phrase skipping and wraparound. The dense polyphony case uses four notes per step on both polyphonic tracks, producing 15 voices per step. Separate observations capture source start deadlines, event sequences, actual audio-thread onsets through a nine-input AudioWorklet, rendered phrase-marker transitions, and visual callbacks. The source receives no product modifications.

The worklet tap observes track gains before master effects; it proves render-thread alignment, not acoustic speaker output or final processed waveform purity. The browser's output timestamp estimates the device playback clock. Its reported output latency here is approximately 96 ms; no microphone or external loopback was used. Visual output-lead estimates are device-dependent and are not acoustic measurements. Onset-to-schedule errors use nearest-time matching and are ambiguous when overload collapses consecutive pulses; do not read that column as a complete latency measurement under severe stalls. Per-track onset matching chooses the nearest partner per track; the exact worst event is preserved in worst-track-skew.json. Synthetic samples isolate scheduling from unavailable library files. Effect-chain quality is covered separately by existing audio gates.

## Findings

### F1 — Phrase marker advances one step early

`src/engine/scheduler.ts` calls `advancePhrase(time)` immediately after scheduling step 63. That function changes `playingPhrase` immediately and schedules `onPhraseChange` at the final step's timestamp, not the first timestamp of the next phrase. The independent marker observation confirms the early transition at each populated-phrase boundary. Mid-lookahead UI actions can expose the already-advanced scheduler state even earlier. Existing tests assert marker presence only during the first phrase and cannot catch this.

Required regression: populate multiple phrases, correlate each marker transition with that phrase's first rendered onset, and include 40, 120 and 220 BPM, skipped empty phrases, song wrap and simultaneous view/edit actions.

### F2 — Playhead uses render time without compensating device output latency

The playhead aligns with `AudioContext.currentTime`, but estimated device playback remains roughly 90–100 ms behind on this machine. At 220 BPM a step lasts 68.18 ms. The existing median-currentTime test can therefore pass while the visible step precedes estimated audible output by more than one step. Measure against `getOutputTimestamp()` and validate with an external audio loopback before claiming acoustic synchronization.

### F3 — Main-thread scheduling loses timing under long tasks

Measured: 396 of 2,016 sources missed their deadlines, with a maximum miss of 114.70 ms. One nine-track onset split across audio blocks: tracks 0 and 1 started at 15.05233560090703 s; tracks 2–8 at 15.055238095238096 s, a 2.90249 ms skew. All nine carried the same scheduled timestamp (14.988441558441636 s). The audio-thread trace caught a defect that comparing scheduled event timestamps cannot detect. Only 199 distinct track-0 onsets were observed for 224 scheduled steps (final stop cancels a small lookahead tail; overload can coalesce adjacent pulses).

The 180 ms periodic-stall scenario deliberately exceeds the approximately 100 ms scheduling lookahead. Inspect the late-source, onset and visual metrics above and the raw trace. Any past-deadline source starts demonstrate that a strong reliability claim needs an explicit load envelope or a scheduling architecture that survives such stalls. Browser jank is deliberately injected; this is a robustness limit, not a claim of the same delay under idle conditions.

### F4 — Production worklets fail to initialize

`npm run build` succeeds, but a browser against `vite preview` reports `Unable to load a worklet's module.` The production UI has one extension/engine icon rather than seven and zero playhead highlights after Play. `src/engine/worklet-loader.ts` imports TypeScript worklets with `?url`, and the emitted `.ts` assets retain TypeScript syntax such as `readonly number[]` and `private model: number`. The compiler/build gate does not exercise the built app. Smoke evidence records this independently of timing instrumentation.

Required gate: build, serve `dist`, initialize all worklets, play a real/generated sample and verify advancing visuals plus the complete extension chain.

### F5 — Real sample loading is blocked and terminates local Vite

Opening the first real drum sample raised `EPERM: operation not permitted, open '<repository>/DRUMS/01. Individual Hits/01. Bass Drum/BD 2600 01.wav'`. Vite terminated with an unhandled ReadStream error, and the browser reported connection refused. The library targets are inside macOS Downloads. This is a local filesystem-access blocker; the exact OS privacy/ACL cause is not established. The server was restarted. Absolute machine paths in the published report and test logs are normalized to `<repository>/`; raw audio traces contain synthetic timing observations only. No permissions, library files or symlinks were changed. Grant access or use an accessible library before testing real sample playback.

### F6 — Existing transport test is unstable

The initial full suite passed 73/74. `Transport Sync / remains in sync after repeated edit + stop/start cycles` failed at its baseline count assertion: expected at least four events, observed three, before the stress phase. Its 1.6 s capture window sits near the fourth beat at 120 BPM plus startup/lookahead. In five repeats of each of four sync tests, 16/20 passed: the transport test failed four times and passed once; the three UI synchronization tests passed all 15 runs. The independent render-onset measurements remained aligned under ordinary load. Do not interpret the short-window failure alone as proven inter-track drift; the independent audio onset traces distinguish that question.

### F7 — Context uniqueness assertion has a blind spot

Instrumentation installed before app scripts sees two AudioContexts: one suspended, one running. The existing uniqueness test patches construction after page load and cannot observe the first. The unused suspended context does not itself establish clock drift; binding and physical output timing require separate assertions.

### F8 — Historical proof is incomplete

The explicit baseline-range gate reports 24 historical product commits missing required governance trailers and 114 passing commits. Missing mandatory proof is BLOCKED. No baseline advancement or history rewrite was performed.

## Follow-up ownership

Product corrections require a Worker-Agent under this repository's governance scope. Priorities: production startup; phrase boundary timestamp/state separation; device-output timing; robust scheduling under long tasks. Governance prevention should add production-runtime checks and independently measured timing thresholds. Existing PR #38 remote checks are green at the tested SHA, demonstrating the current coverage gap.

The six scenarios exercised 1,380 steps and 14,712 source starts, including 40 rapid restart cycles. `runtime-checks.json` records explicit per-scenario PASS/FAIL checks. The app remains available on port 5173. This audit does not certify Firefox, Safari, mobile browsers, external MIDI clock, hardware loopback timing, background-tab resilience or multi-hour playback.
